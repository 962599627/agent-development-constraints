# 精简流程（PRUNE）

> 目标：**对抗规则库膨胀**。
>
> 核心事实：**约束的价值随长度递减**。L0 超过 15 条，AI 会开始忽略它们 ——
> 届时规则库不但没帮忙，反而挤占了它本该读的代码上下文。

---

## 什么时候精简

- 每个月
- 或每积累 10 条新规则
- 或 **L0 超过 15 条时（这是硬触发，必须立刻处理）**

## 四项操作

### ① 合并（同类抽象）

多条规则在说同一件事的不同侧面时，合并成一条更抽象的。

**判断方法**：写下两条规则的"违反场景"，如果场景高度重合 → 合并。

**例**：
```
合并前：
  R-A 数据库密码不要写进 settings.py
  R-B Composer 文件里不要写死 MySQL 密码
  R-C 文档里不要记录管理员密码

合并后：
  R-001 凭据绝不硬编码（源码 / 配置 / 文档 / 模板 全都不行）
```

**注意**：合并时保留**代价最高**那条的证据，其余证据挪到"相关案例"里。

### ② 降级（L0 → L1 / L2 / L3）

L0 是稀缺资源。下面情况要降级：

| 情况 | 降到 | 理由 |
|---|---|---|
| 只适用于某技术栈 | **L2** | 换项目就失效 |
| 违反代价不高（只是慢一点） | **L1** | 不值得占铁律名额 |
| 已被工具链自动拦住 | **删除** | linter/formatter/CI 已经做了 |
| 半年没被触发过 | **L3 归档** | 但**保留**，避免重新发现 |

### ③ 改写（让检查可自动化）

**这是精简中最有价值的一步**。把不可执行的规则改造成可执行的。

**改造前**：
```
- 规则：注意不要泄露用户隐私
- 检查：人工 review
```

**改造后**：
```
- 规则：公开接口默认只返回 id + 展示名；邮箱/账号/内部标记必须显式且仅本人可见
- 检查：未登录请求每个公开列表接口，断言返回的嵌套用户对象字段集合 == {id, display_name}
```

**判据**：改写后能不能写出一条**断言**或一条**命令**？能就说明改造成功了。

### ④ 删除（只删被替代的）

**只有两种情况可以真删**：
1. 已被工具链强制（有 linter 规则、CI 检查）
2. 与其他规则完全重复（合并后）

其他情况一律**降级到 L3 归档**，不要删 —— 归档的成本极低，而重新发现同一个坑的成本很高。

## 精简时的自检清单

```text
□ L0 条数 ≤ 15 ？
□ 有没有两条规则描述同一个违反场景？（→ 合并）
□ 有没有规则的"检查"写的是"人工检查/注意"？（→ 改写或降级）
□ 有没有规则从未被触发过？（→ 降级到 L3）
□ 有没有规则该由工具链管？（→ 删除）
□ 每条 L0 规则的「证据」是否还在？（证据丢失 = 后人会误删）
□ 变更日志是否记录了本次精简？
```

---

## 可用的精简提示词

```text
你是一个约束库的精简器。下面是当前的约束库。

请按以下顺序处理，并解释每一步的取舍：

1. 找出描述同一违反场景的规则 → 提议合并，给出合并后的表述
2. 把 L0 里满足以下任一条件的标出来 → 提议降级：
   - 只适用于特定技术栈（→ L2）
   - 违反代价不高（→ L1）
   - 已被 linter / formatter / CI 覆盖（→ 删除）
3. 把「检查」字段无法自动化的规则挑出来 → 改写成一条命令或一条断言；
   改写不了的，标记为待降级
4. 把半年未触发的规则 → 提议移入 L3 归档（不要删除）
5. 输出精简后的完整约束库，并给出：
   - L0 从 N 条变成 M 条
   - 哪些条目被删除了、为什么

要求：宁可保留也不要误删。只有"已被工具链强制"和"完全重复"才允许真删。
```

---

## 精简之后

1. 更新 `constraints.md` 的**变更日志**（精简也是一次变更，要留痕）
2. 对照新旧版本，确认**没有误删还需要的规则**（用 git diff 看）
3. 如果删掉了某条规则，在 **L3 归档**里留一行说明"被什么替代了"
