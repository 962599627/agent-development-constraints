# 开发约束库

> 本文件是**唯一需要 AI 读取**的约束产物。其余文件都是"如何维护它"的流程说明。
>
> **维护铁律**：L0 区不超过 15 条。超了就必须合并或降级 —— 约束一旦膨胀，
> AI 会开始忽略它们，届时不写反而更诚实。

---

## 怎么读这份文件

每条规则包含四个部分，**缺一不可**：

| 字段 | 作用 | 没有它会怎样 |
|---|---|---|
| **规则** | 一句话的可执行约束 | 变成"注意安全"式的废话 |
| **触发** | 什么时候该想起来 | AI 想不起来，等于不存在 |
| **检查** | 怎么验证有没有违反 | 无法自动化，只能靠自觉 |
| **证据** | 哪次真实踩坑换来的 | 后人不知道轻重，容易删掉 |

## L0 · 铁律

> 跨项目通用、违反代价高、**必须有自动化检查方法**。
> 上限 15 条。新增一条就要考虑踢掉一条。

### R-001 凭据绝不硬编码
- **规则**：密钥、密码、token 只能从环境变量/密钥管理读取，**绝不写进源码、文档、配置模板**
- **触发**：新建配置文件、连接数据库、写部署脚本、建 `.env.example`
- **检查**：在源码里搜字面量形式的密码赋值：
  `(PASSWORD|SECRET|TOKEN|KEY)\s*[:=]\s*["'][^"']{6,}["']`
- **证据**：2026-04-25 三处明文密码（`settings.py` / `docker-compose.yml` / `项目大纲.md`）随首次提交进入 git 历史
- **代价**：凭据泄露；补救要轮换密码 + 重写 git 历史

### R-002 忽略规则防不住"已经写进去的值"
- **规则**：`.gitignore` 只能防未来新增的文件。**判断一个文件是否安全，要看内容里有没有值，而不是看文件名是否被忽略**
- **触发**：配置 `.gitignore`、准备首次提交、准备开源
- **检查**：`git grep -n -I -E '<敏感值>' HEAD` —— **直接在当前提交内容里搜**
- **证据**：R-001 同一次事故 —— `.gitignore` 排除了 `.env`，但密码本来就在 `settings.py` 里
- **说明**：这条与 R-001 互补：R-001 防"写"，R-002 防"以为没写"

### R-003 全局副作用必须带测试开关
- **规则**：任何**跨请求共享状态**的机制（限流计数、缓存、单例、连接池、全局标记），
  必须提供一句话就能关闭的开关，否则它会污染测试
- **触发**：新增限流/缓存/熔断/全局状态
- **检查**：跑完整测试套件，看是否出现"单独跑通过、一起跑失败"的用例
- **证据**：2026-04-25 加登录限流（10 次/分钟）后，因所有用例共用缓存计数，
  **整个套件炸出 37 个错误**；第 11 个之后的用例全被 429 挡住
- **修法参考**：`settings` 里用 `sys.argv` 判断测试环境默认关闭，需要验证限流的用例自己打开

### R-004 显示名与标识必须分开
- **规则**：对外展示用一个可变字段（昵称），**路由、查询、身份判断必须用不可变标识（ID）**
- **触发**：任何"跳转到某人主页""查某人的数据""判断是不是本人""按名字查询"
- **检查**：grep 路由与查询串里是否出现 `username` / `name` 之类可变字段
- **证据**：2026-04-25 主页 URL 用用户名暴露账号；团队逐处核对时需要专门列一张表区分两类用法
- **典型翻车**：身份判断写成 `当前用户.用户名 === URL里的用户名` → 一旦 URL 换成 ID，**本人主页会被判定为"他人"**，编辑按钮全部消失

### R-005 HTML 结构必须合法（列表项里别塞按钮）
- **规则**：可点击的整行 + 行内按钮，必须是**兄弟节点**，不能嵌套成 `<a><button>` 或 `<a><a>`
- **触发**：列表项既要整行跳转、又要放操作按钮
- **检查**：检查渲染出的 DOM 是否有 `<a>` 嵌套交互元素
- **证据**：2026-04-25 关注列表加按钮时，`<a><button></button></a>` 导致 HTML 非法 + 点按钮误跳转
- **修法参考**：外层改为 flex 容器，链接 `flex-grow-1` 占左侧，按钮作为兄弟放右侧

### R-006 用户可控的查询参数必须在视图层校验类型
- **规则**：请求参数直接进 ORM 过滤/类型转换前，必须先安全转换，非法值回退默认分支
- **触发**：写列表接口的过滤、分页、排序参数
- **检查**：手工构造非法值请求（`?id=abc`、`?page=1.5`、空值），确认**不是 500**
- **证据**：2026-04-25 `?follower=abc` 直接被 `filter(follower_id='abc')` 抛 ValueError → **500**；
  前端加了守卫也没用 —— 攻击者改 URL 就能绕过前端
- **要点**：前端的校验是体验，**后端的校验才是防线**

### R-007 公开接口默认不返回隐私字段
- **规则**：任何**未登录可访问**的接口，其嵌套的用户对象默认只给 `id` + 展示名；
  邮箱、账号、内部标记（`is_staff`）、私人设置必须**显式**才给，且只在本人视角给
- **触发**：新增公开列表接口、或往公开接口里嵌用户对象
- **检查**：未登录请求该接口，逐字段核对返回内容
- **证据**：2026-04-25 `/api/profiles/` 未登录即可拉取**全部用户的邮箱与账号**，
  连用户自己的"是否公开邮箱"开关都被绕过

### R-008 热重载不可用时，改动后必须重启
- **规则**：服务以"关闭热重载"方式运行时（`--noreload` 等），**代码改动不会自动生效**，
  必须重启进程再验证
- **触发**：启动服务、改完代码准备验证
- **检查**：改一行代码 → 看进程 PID 是否变化 / 行为是否更新
- **证据**：2026-04-25 多次出现"改完没生效"，浪费排查时间；且提权实例无法用常规方式结束进程，
  要用 WMI `Invoke-CimMethod -MethodName Terminate`

### R-009 测试失败要区分"真的坏了"和"被污染了"
- **规则**：一次改动导致**大批**用例失败（尤其报错集中在认证/限流/连接）时，
  先怀疑**共享状态污染**，而不是逐个改用例
- **触发**：跑完整套件出现大面积非预期失败
- **检查**：单独跑失败用例是否通过 → 是的话基本确认是污染
- **证据**：R-003 的 37 个错误；正确修法是让全局机制可关闭，而不是去改 37 个用例

### R-010 入口缺失会让隐藏 bug 永远藏住
- **规则**：数据已经有、但**没有入口能看到**时，视为功能未完成 —— 因为错误无法被发现
- **触发**：做统计数字、计数、状态展示
- **检查**：每个展示出来的数字，问一句"点进去能看到明细吗"
- **证据**：2026-04-25 粉丝列表接口恒返回 0（`?followed=` 被 `follower=me` 过滤吃掉），
  但主页数字是对的，**藏了很久没人发现**；直到做了可点击弹窗才暴露
- **附带收益**：补入口之后，应同步加一条**一致性测试**（列表条数必须等于计数）

### R-011 两个地方说同一件事，就必须有一致性测试
- **规则**：同一个事实被两处呈现（列表条数 vs 计数字段、缓存值 vs 源数据）时，
  必须有一条断言它们相等的测试。
  **副本超过两处时，优先"收敛到一个来源"，而不是给每个副本配一条测试。**
- **触发**：实现统计/计数/摘要类字段；
  **以及任何"版本号 / 配置值 / 枚举清单 / 依赖列表"被抄写到多处时**
- **检查**：
  1. 先把**所有副本列出来** —— 特别注意那些"不像代码"的地方：
     - 源码常量、配置文件、`VERSION`、`package.json`
     - 文档与注释（README、CHANGELOG）
     - **commit message、PR 描述、发布说明**
     - CI 配置、部署脚本、模板
  2. 对**能被测试覆盖的**副本加"两处相等"的断言
  3. 对**测试管不到的**副本（commit message / 发布说明 / PR 描述），
     **必须先读真实来源再写，不要凭记忆** —— 这是唯一防得住的办法
  4. 副本超过 2 个 → 先想"能不能只留一个来源"（如统一读 `VERSION` 文件），
     再对剩下的加测试
- **证据**：
  - **R-010 同一次**：加上"粉丝列表条数 == profile 的 followers_count"这条断言后，
    这类"各说各话"的问题再也藏不住
  - **2026-10-05 插件版本号三处漂移**：同一个版本号被写在**三处** ——
    `VERSION` 文件、host 状态路由里硬编码 `'0.11.0'`、client 里硬编码 `'0.9.0'`。
    升级时只改了第一处，于是卡片**永远显示 0.11.0**，用户重启多次都没用，
    排查也一直找错方向。
    修法不是"给三处各加一条测试"，而是**收敛到单一来源**
    （host 用 `readOwnVersion()` 读 `VERSION`，client 由 host 上报），
    再给剩下两处加一致性测试。
  - **同日的后续翻车（这条最有价值）**：加了测试之后，版本号在
    **源码与 `VERSION` 文件**之间确实一致了，测试也全绿。
    但我在 **commit message 里随手写了 `v0.18.0`**，而真实版本是 `0.17.0`。
    **测试覆盖不到 commit message** —— 这正是"副本清单"必须**显式列出**的理由：
    **测试管不到的地方，就是最容易漂移的地方；
      而"三处数据源都对"会让人误以为"这个问题已经解决了"。**

### R-012 非法/异常路径要有测试，不能只测happy path
- **规则**：新增接口至少覆盖：非法参数、空值、越权访问、边界值
- **触发**：写新接口或新页面
- **检查**：看测试用例里"预期失败"的比例
- **证据**：2026-04-25 R-006 的 500、R-007 的泄露，都是**只测了正常路径**才会漏

### R-013 测试夹具不得使用生产级成本的操作
- **规则**：测试环境必须把"真贵"的操作换成廉价替身（密码哈希、加密、转码、网络、外部命令）。
  **框架自己不会替你降级** —— 必须显式配置。
- **触发**：新增测试夹具（建用户、造文件、发请求）；或觉得"测试怎么这么慢"
- **检查**：跑 `--durations N` 看最慢用例；
  **若耗时是某个常数（0.25s / 1s）的整数倍，那就是哈希/加密成本，不是 IO 或逻辑**
- **证据**：2026-10-05 某项目 511 个用例跑 **150 秒**，用户直接质疑
  "以我电脑性能是极快的，这明显有问题，应该存在严重 bug"。
  用 Django 的 `--durations` 定位，最慢用例耗时**全是 0.25s 的整数倍**：
  `PBKDF2 iterations = 1,200,000` → 一次 `make_password` = **0.250 秒**，
  而 **Django 的 `setup_test_environment()` 不会自动换成快速哈希器**。
  对照实验（同一条命令，只差一个环境变量）：

  | 条件 | 结果 |
  |---|---|
  | 默认（生产级 PBKDF2） | **149.0s** |
  | 测试用 `MD5PasswordHasher` | **5.5s** |

  差距 **27 倍**，用例数完全相同（511）且全部通过。
- **怎么防**：
  ```python
  if "test" in sys.argv and not os.getenv("KEEP_SLOW_HASHERS"):
      PASSWORD_HASHERS = ["django.contrib.auth.hashers.MD5PasswordHasher"]
  ```
  并留一个环境变量开关，需要时能切回真实哈希做对照 —— **这条规则本身就是靠那个开关证的**。

### R-014 扫描/审计工具报「没问题」之前，先证明它能报出已知问题
- **规则**：任何静态扫描、泄漏审计、死代码检测，输出前必须做**已知阳性验证**：
  准备一个"必定会被发现"的样本，确认工具能报出来，再相信它的"0 处问题"。
- **触发**：写扫描脚本；或看到"扫描结果：0 处问题"
- **检查**：脚本里有没有针对自身的自测（喂一个已知坏样本，必须报警）
- **证据**：2026-10-05 同一次任务里，我写的检测脚本连续出现 **5 处假阴性**，
  每一处都会让人误以为"没问题"：

  | 脚本写法 | 后果 |
  |---|---|
  | `getattr(模型类, "video_file")` | 拿到的是**描述符**而非 `FileField`，永远匹配不上 → 把真实泄漏报成"无"（正解：`model._meta.get_field()`） |
  | `<template>(.*?)</template>` 非贪婪 | 遇到嵌套 `<template>` 就截断，漏扫后半段 |
  | 正则 `["']…["']` 混合引号 | `'a'` 的引号被相邻匹配吃掉，**在用的类名**被报成死代码 |
  | 内层 `{1,80}` 不允许空串 | `cond ? '' : 'real'` 的空串破坏引号配对 |
  | 只扫 `<script>` 找拼接前缀 | `:class="'x-' + v"` 写在**模板**里，漏判 |

  其中第一条直接造成"泄漏审计报告 0 处"，而实测**未登录可下载 14.7MB 原片**。
- **反直觉点**：假阴性比假阳性危险 —— 假阳性只是噪声，
  假阴性会让人**停止排查**并宣布"已确认安全"。

### R-015 改数据源会激活「从未执行过的分支」，按新功能对待
- **规则**：把输入从 A 换成 B（mp4→HLS、同步→异步、单档→多档）时，
  等于**第一次运行**代码里那段"为 B 写但从没走到过"的分支。
  不能因为"这段代码早就在仓库里"就默认它是好的 —— 必须端到端验证。
- **触发**：修改数据来源/格式/协议；或"这段代码看起来很完整"
- **检查**：看该分支的入口条件，问一句"**在这之前它有机会被执行吗？**"
- **证据**：2026-10-05 轮播图预览从 mp4 改成 HLS，**一次暴露 3 个从未发现的 bug**：
  1. `ref="el => …"` **漏冒号**（Vue 函数 ref 必须写 `:ref`）→ 被当成字符串 ref 名，
     箭头函数永不调用 → hls.js 从未启动 → **视频不播，且没有任何报错**
  2. 自定义 `xhrSetup` 强制 `responseType="text"` 并重写 `xhr.send`
     （项目文档里**早就警告过**这种写法）
  3. 缺"引用未变就返回"的守卫 → 回调里写响应式状态 → `Maximum recursive updates exceeded`

  一直没暴露的原因：旧数据源下这段代码根本不需要 ——
  `<video src>` + `autoplay` **属性**自己就能播。
- **判据**：「**没反应 + 没有报错**」≈ 代码根本没执行，而不是"执行了但失败"。
  有报错反而说明它跑起来了。

### R-016 改插件/依赖源码后，必须更新「安装态副本」并重启宿主
- **规则**：源码目录 ≠ 运行中的那份。改完源码要**显式更新安装态**，
  并在宿主**重启**后才算生效；只提交源码等于没改。
- **触发**：修改插件、被 `file:` 引用的本地依赖、已安装到项目的规则库；
  或"改完代码但行为没变"
- **检查**：
  1. 宿主**实际加载**的是哪个路径（不是你以为的那个）
  2. 该路径下的文件是否含你的改动（比对版本号或直接搜新函数名）
  3. 宿主进程是否已重启
- **证据**：2026-10-05 我给一个 DSH 插件连做了 6 个提交（含新增动作、
  注入内容改造、规则扩充）并全部推送，**但用户一句"我都安装插件了
  应该更新到插件里了"点破了问题**。实测：

  | 位置 | 状态 |
  |---|---|
  | `F:\agent-constraints`（源码，我一直在改） | 0.26.2 ✓ |
  | `~\.dsh\profiles\desktop\node_modules\agent-development-constraints`（宿主实际加载） | **0.24.0 ✗** |

  根因：profile 里声明的是 `"agent-development-constraints": "file:F:/agent-constraints"`，
  而 **npm 对 `file:` 依赖是"安装时拷贝一份"**（非软链），
  之后源码怎么改都不影响已安装的那份。再加上宿主进程已经把旧 `index.mjs`
  import 进内存，即使文件更新了也要**重启**才加载。
- **怎么防**：
  - 改完源码立刻把**安装态**一起更新（`npm pack` 后覆盖安装目录，
    或在 profile 目录重跑安装），并核对该目录里的版本号
  - 把"重启宿主"写进交付说明 —— 用户没重启时，你看到的行为仍是旧的
- **同族**：R-008（热重载不可用时改动后必须重启）——
  R-008 说的是"进程要重启"，本条规定"**先要有一份新的东西可加载**"。

## L1 · 协作约定

> 人和 AI、AI 和 AI 之间的协作规则。违反不致命，但会显著降低效率。

### C-001 并行写手的工作范围必须互斥
- **规则**：派发并行任务时，每个执行者的**写入文件集合必须不重叠**；重叠时必须排队
- **触发**：拆分任务、派多个执行者
- **检查**：把各任务的写入路径列出来，检查交集
- **证据**：2026-04-25 多个任务期间出现"文件被并发改写、行号漂移"，
  执行者需要重新 grep 确认自己的改动还在

### C-002 交接信息要带证据，不要只说"已完成"
- **规则**：交付时必须附：命令输出、改动前后对比、未覆盖的情况
- **触发**：任何任务交付
- **检查**：看交付里有没有可直接复现的命令
- **证据**：2026-04-25 多位执行者主动附了 `type-check` 输出与 grep 复核结果，
  使验收成本大幅下降；反之"已完成"三个字无法验收

### C-003 执行者要敢于报告"你给的契约不完整"
- **规则**：发现上游给的接口/约定有缺口时，**先按契约实现，同时明确报告缺口与建议**
- **触发**：实现过程中发现契约缺字段/缺参数
- **检查**：—
- **证据**：2026-04-25 执行者发现 `FollowViewSet` 缺 `?follower=`，
  按契约做完并加了如实提示，同时报告建议 —— 上游随后补上，避免了"数字是别人的、列表是我的"

### C-004 记录要沉淀成规则，不能只写故事
- **规则**：写完一篇开发记录后，问一句"**这里有没有可以变成下次自动生效的约束**"；
  有就提炼到本文件
- **触发**：完成一个功能、修完一个 bug
- **检查**：本文件最近一次更新是否晚于最新开发记录
- **证据**：本项目开发记录已 538 行，但约束区长期只有 2 条 —— 教训没生效，才会重复踩

### C-005 面向人的命令不要有长等待循环
- **规则**：给别人（用户/同事）跑的命令，**单次执行不应可能等待超过约 30 秒**；
  需要重试或耗时操作就**丢到后台**，并明确告知"在跑，出结果通知你"
- **触发**：写脚本、跑网络操作、批量任务
- **检查**：命令里是否有 `Start-Sleep` / 重试循环 / 可能阻塞几十秒的调用
  （如 `Test-NetConnection` 默认要等 20 秒以上）
- **证据**：2026-04-25 推送仓库时写了「重试 6 次 × 每次 sleep 10 秒」的循环，
  网络不稳时长达数分钟零输出，被误判为卡死，用户连续追问"卡了吗""卡了"

### C-006 别用"重试 + 长等待"对付网络问题，先分层诊断
- **规则**：网络操作失败时，**先分辨是应用层还是传输层**，再针对性修；
  不要用无脑重试拖延
- **触发**：`git push` / `fetch` / curl 失败
- **检查**：诊断顺序 —— ① `curl --max-time 5` 看 HTTPS 是否通
  ② 通则说明**网络没问题**，问题在客户端传输层（见 L2 的 `http.version`）
  ③ 仍不通再考虑重试或换网络
- **证据**：2026-04-25 `git push` 连续两次报 `Failed to connect ... port 443`，
  但同一时刻 `curl https://github.com` 返回 **200** —— 网络没问题，是 git 在 HTTP/2 上挂起

### C-007 改了结构就要回头改文档
- **规则**：变更**目录结构 / 版本号 / 核心概念**时，必须**同步**更新 README 与相关说明。
  文档里出现的路径必须是**真实存在**的
- **触发**：新增或删除顶层文件、拆分模块、改版本号、重命名概念、调整安装流程
- **检查**：**只查真实的 markdown 链接**（`[text](path)`）是否存在：
  ```bash
  grep -oE '\]\([^)#[:space:]]+\.(md|sh|ps1)\)' README.md \
    | sed -E 's/\]\((.*)\)/\1/' | grep -v '^http' | sort -u \
    | while read -r f; do [ -e "$f" ] || echo "失效链接: $f"; done
  ```
  版本号也要核对：README 里写的版本是否等于 `cat VERSION`

  > ⚠️ **别把代码块里的文件名也拿去检查**。像 `python.md` / `git.md` 这类是
  > **示意路径**（安装后才存在于目标项目，或相对于 `core/`），
  > 用宽松正则会跑出一大堆误报 —— 这条规则**第一次使用时就踩了这个坑**，故修正为只查链接。
- **证据**：agent-constraints（2026-04）README 长期停留在 `0.1.0` ——
  版本号、目录结构、L2 描述**全部过时**，而 0.2 / 0.3 两次迭代都没回头改它；
  读者会照着不存在的路径找文件
- **代价**：文档漂移会让人**照着错的信息操作**，比没有文档更糟

### C-008 每次提交前必须过脱敏检查
- **规则**：任何**可能被他人看到**的输出（公开仓库、共享仓库、日志、截图、issue）
  在产生前都必须过脱敏检查。**这四类一律不得出现**：
  ① 凭据（密码/密钥/token/连接串）
  ② **本地绝对路径**（含本机用户名、目录结构）
  ③ 个人信息（邮箱、手机号、账号）
  ④ 项目专名与内部代号
- **触发**：`git commit` / `git push` / 发布 / 贴日志与截图 / 提交 issue
- **检查**：**做成自动的，别靠记得**
  - 本仓库已提供：`scripts/sanitize-check.ps1`（配 `.sanitize-deny.txt` 黑名单）
  - 已装为 **pre-commit hook**（`scripts/install-hooks.ps1` 一键启用）
  - 没有工具时手工搜：
    ```bash
    git grep -nEi '(password|密码|token|secret)\s*[:=]'
    git grep -nE  '[A-Za-z]:\\Users\\'
    git grep -nE  '1[3-9][0-9]{9}'
    ```
- **证据**：agent-constraints（2026-04）准备公开仓库时发现
  **31 处项目专名**与一个把本地路径 `F:\python2` 写进**文件名**的示例文件 ——
  都是"当时觉得无所谓"留下的
- **⚠️ 关键认知**：脱敏**只在内容被"写进去"的那一刻有效**。
  一旦提交，git 历史里就**永久留下**了（改文件没用，见 **R-002**）——
  所以检查必须发生在**提交之前**，而不是"公开之前"

### C-009 装进别人运行环境的代码，任何失败都只能降级
- **规则**：插件 / 库 / 中间件 / 钩子这类"跑在宿主里"的代码，
  任何一段失败**只允许降级**（功能不可用），**绝不能把宿主拖垮**
- **触发**：写插件入口、注册钩子、实现宿主回调、发布给别人安装的东西
- **检查**：
  1. 初始化入口（`apply()` 之类）**每一段**都包 try/catch
  2. 宿主回调对**畸形输入**一律原样透传，不改写宿主的决定
  3. 不在顶层 import"宿主承诺会提供"的包 —— **承诺不等于装上了**
  4. 交付前在**真实宿主**里加载一次，而不是只跑单测
- **证据**：agent-constraints 自身（2026-10-05）。插件顶层
  `import { defineTool } from '@deepseek-ai/dsh-tools'`，而目标 profile 设了
  `autoInstallPeers: false` → 该包从未被安装 → 模块解析失败 →
  插件加载态 FAILED → **宿主会话直接崩溃**
  （`Cannot read properties of undefined (reading 'kind')`），用户只能手动禁用
- **代价**：用户的工作环境中断；信任受损（"装你的东西把我的应用搞崩了"）
- **独立发现次数**：1（待更多项目验证后考虑升级 L0）

### C-010 假依赖会掩盖真实的环境问题
- **规则**：测试里造的 stub / mock，如果是为了让"本该存在的东西"看起来存在，
  它同时屏蔽了**"它不存在"**这个最该被看到的信息
- **触发**：为了让 import 成功、让测试跑起来而造 stub 时
- **检查**：
  1. 能用真实依赖就用真实的
  2. 必须造 stub 时，**另加一条不用 stub 的用例**，或加静态检查
     （例如"依赖清单里不得出现 `node:` 以外的外部包"）
  3. 每次造 stub 前问一句：**"如果这个东西真的不存在，我的测试会红吗？"**
     —— 如果不会，那这个 stub 正在掩盖问题
- **证据**：同一次事故。插件测试原本自造 `@deepseek-ai/dsh-tools` 的 stub，
  **11 个用例全绿**；而真实环境里没有那个包 → 加载失败、宿主崩溃。
  事后回看：**当时的全绿是有害的** —— 它让人相信"已经验证过了"。
  与 **C-002** 呼应：证据要能支撑结论，**假环境里的绿不算证据**
- **独立发现次数**：1
- **与 R-001 的关系**：R-001 防"**写**"（凭据别硬编码），
  C-008 防"**提交**"（连带路径、身份、项目名一起过筛）。两条互补

### C-011 常驻成本要算总账：能按需就别常驻
- **规则**：任何"**每轮都要发送**"的东西 —— 工具 description、系统提示里的段落、
  `pre-step` 注入的提示 —— 它的成本是 **单次大小 × 轮数**，不是单次大小。
  **写进上下文（尤其写进历史）= 订阅制；做成按需查询 = 按次付费。**
  同样一份信息，两者的成本可能差几个数量级。
- **触发**：往系统提示 / 工具描述 / 注入 / 任何"会被反复发送"的地方加内容时
- **检查**：
  1. 这条信息是"**每轮都需要**"还是"**需要时才要**"？
  2. 如果它已经能通过工具 / 文件按需取得，**就不要写进常驻区** ——
     信息量相同，但一份是零常驻成本
  3. 算一次总账：`单次 tokens × 预计轮数`，而不是只看单次大小
  4. **特别检查**：注入的消息会**进入 session 历史**，之后每轮重发 ——
     所以"每步注入"的真实成本是 `大小 × 步数 × 后续轮数`
  5. 给"只在需要时发生一次"的操作加**去重**（如 WeakSet 记录已处理对象）
- **证据**：agent-constraints 插件（2026-10-05）。`pre-step` 注入最初每步写
  454 字符（约 284 tokens）并列出全部 12 条 L0 铁律标题。一个 turn 若有 5 步，
  就是 5 条注入进历史、之后每轮重发。
  改为"**一句话指路 + 每会话只注入一次**"后降到 41 tokens ——
  **信息量没有减少**（工具随时可查 `l0`），只是从"每轮订阅"变成"一次指路"。
- **⚠️ 最反直觉的一点**：当初列全部铁律是**出于好意**（"让 AI 一眼看到约束"）。
  好心反而制造了成本 —— **"信息更全"不等于"设计更好"**，
  在上下文稀缺的系统里，"少而按需"往往优于"全而常驻"
- **独立发现次数**：1

### C-012 给数据打报告，不要凭印象
- **规则**：客户端已经启动？插件真的加载了？错误发生在哪一段？——
  这类问题**不要靠读代码推断**，而是让程序**把事实写到磁盘**，再读它
- **触发**：排查"看起来应该工作但没有工作"的问题；连续两次以上的推测落空时
- **检查**：
  1. 先问"我需要知道哪些**具体事实**"，然后写一个**探针**把它们记下来
     （阶段名、时间、关键对象的类型/键名/值，而不是"我觉得"）
  2. 探针写在**最早可能的位置**，保证即使后续崩溃也会留下记录
  3. 探针要**累积**而不是覆盖 —— 只看最后一条会漏掉"哪条路径真的成功"
  4. 失败分支**必须留痕**：静默跳过 = 把最难查的问题留给自己
  5. 探针本身失败绝不能影响主流程（全程 try/catch）
- **证据**：同一次插件开发（2026-10-05）。同一个"工具不出现"的现象，
  **凭代码推测三次全错**：先怪顶层 import，再怪 `pre-step` 透传 undefined，
  再怪 `ctx.inject` 用法。第四次改为写探针，一次就定位到：
  ```
  { "stage": "tool-register-skipped", "reason": "ctx.tools 不存在",
    "ctxKeys": ["on"] }
  ```
  ——**插件确实加载了**，只是 `export const inject` 被我自己删掉了。
  后续"每步注入的契约"（`kind:'enter'`、messages 是数组、payload 含 agent）
  也全靠探针一次拿到，而不是继续读文档猜。
- **独立发现次数**：1
- **与 C-002 的关系**：C-002 要求**交付**时带证据；C-012 要求**排查**时先造证据。
  两者是同一条原则的两端：**结论必须有事实支撑，无论是对人还是对自己**

### C-013 静默的部分成功：没报错 ≠ 拿全了
- **规则**：一个 API **成功返回、没有抛异常**，**不等于它返回了全部内容**。
  凡是**流式 / 分块 / 多帧 / 分页 / 增量追加**的读取，
  都必须**独立核对"完整性"**，而不是只看"有没有出错"。
- **触发**：读取压缩文件、分块传输、流式日志、分页 API、
  或任何"一次调用看起来成功、但结果比预期小很多"的场合
- **检查**：
  1. 先问："**这个读取 API 会不会只返回一部分？**"
     （尤其：它处理的是"多个 frame / 多个分片拼起来的文件"吗？）
  2. **主动核对完整性指标**，而不是等报错：
     解出的行数、总字节数、帧数/分片数、翻页游标是否到末尾
  3. **结果异常小时，第一反应不该是"数据本来就这么小"**，
     而是"**我是不是只拿到了一部分**"
  4. 完整性指标要**写进输出或日志**（如 `frames: 20, failed: 0`），
     这样下次不用重新怀疑一遍
  5. 单块失败时**计数并继续**，别让一块坏掉毁掉整体 —— 但**必须把失败数报出来**
- **证据**（2026-10-05，读 DSH 会话文件统计工具用量）：
  `zstdDecompressSync(buf)` 对 1.5 MB 的会话文件**只返回一行会话头**，
  **没有异常、没有警告**。第一反应是"这些文件可能是空的"，
  差点据此得出"该会话没有任何工具调用"的结论。
  真相：会话文件是**流式追加**的，内部是**多个 zstd frame 串接**
  （648 KB 里有 20+ 个 frame，起点 0, 212, 537, 1879, ...），
  而该 API **只解第一个 frame**。
  改为扫描 magic number（`28 B5 2F FD`）逐帧解压后，同一文件解出 124 KB。
  **这个失败如果没被识破，会让"工具用量统计"得出与事实相反的结论**，
  而使用者完全看不到任何异常信号。
- **独立发现次数**：1
- **与 C-012 的关系**：C-012 说"**别靠印象，去拿数据**"；
  C-013 补上下半句："**拿到数据后，还要确认它是不是完整的**"。
  两条合起来才是完整的取证：**先要有证据，再确认证据没缺页**

### C-014 「空」必须被解释：等待态与故障态要分开
- **规则**：任何**在正常情况下会显示为空**的界面 / 接口 / 日志，
  都必须让使用者能区分三种状态：
  1. **还没有**（正常 —— 正在等触发条件）
  2. **取不到**（异常 —— 请求失败 / 加载出错）
  3. **有，但就是空**（真实的空数据）
  三者混成同一个空白，**用户和开发者都会去追一个不存在的 bug**。
- **触发**：设计任何"数据可能暂时不存在"的展示；
  写任何"还没启动 / 还没连接 / 还没收到第一条消息"的等待逻辑
- **检查**：
  1. 先问："这个界面在**正常但数据还没到**的时候会显示什么？"
  2. 那个显示**和"出错了"能不能区分开**？不能就立刻补上
  3. 等待态要同时给出三件事：**在等什么** + **怎么才会不空** + **还在不在努力**
     （如"已重试 3 次 · 最近一次 12:55:31"）
  4. 面向排查的技术细节**默认折叠** —— 平时说人话，需要时才展开
  5. 最坏的写法是「暂无数据」—— 它把上面三种状态全盖住了
- **证据**（2026-10-05，插件设置卡片）：
  卡片的占用数据由 host 在**第一个 `agent/pre-step`**（= 用户发出第一条消息）
  时才产生。用户**在发消息之前**打开设置页，看到一片空白 ——
  **那完全正确**。
  但卡片把"正在等待会话开始"和"出错了"显示成同一个空白，
  于是**用户以为坏了（截图来问），我也以为坏了**。
  接下来五轮误判 —— 缓存旧 bundle / 需完全退出进程 / host 时序缺口 /
  HTTP 响应被缓存 / 重试窗口太短 —— **起点全都是这个没做的区分**。
  最后是用户一句"**是不是还没发消息时截的图**"结束了它。
  真正的修法只有十几行：等待态说人话、故障态给警示、技术细节收进折叠区。
- **独立发现次数**：1
- **与 C-013 的关系**：C-013 说"**没报错 ≠ 拿全了**"（别被"成功"骗）；
  C-014 说"**空 ≠ 坏了**"（别被"空白"骗）。
  再加上 C-012（别被"印象"骗），三条构成同一族：
  **现象不等于结论 —— 先问"这个现象还有别的解释吗"**

### C-015 用户报「慢 / 卡 / 没反应」时先测量，不要先归因于环境差异
- **规则**：用户说慢，先拿数据（耗时、`--durations`、**对照实验**），再下结论。
  **不要**用"你机器/网络/环境不同"把它解释掉。
- **触发**：用户说"太慢 / 卡住 / 是不是有 bug / 这么久不正常"
- **检查**：有没有做**对照实验** —— 同一条命令，只改一个变量，看差异
- **证据**：2026-10-05 我连续几轮把 150 秒的全量测试当成"正常"（还两次因超时被中断、
  拿不到结果），用户直接质疑："以我电脑性能是极快的，这明显有问题，应该存在严重 bug"。
  按要求一测，果然是 **27 倍**差距（见 **R-013**），根因是一行缺失的测试配置。
  **用户的体感判断是对的，我的"环境差异"假设是错的。**
- **延伸**：用户的"体感"往往比我的"解释"更接近真相 ——
  他天天用这台机器，对"该多快"有基准；我没有。

### 构建 / 命令 / 环境

|---|---|---|
| `Failed to connect ... port 443` 但 `curl` 能通 | git 在 HTTP/2 上挂起 | [`stacks/git.md`](stacks/git.md) |
| 退出码 1，但命令实际成功了 | PowerShell 把 stderr 当错误 | [`stacks/shell.md`](stacks/shell.md) |
| 脚本报语法错误 + 中文乱码（`鏅鸿兘`） | `.ps1` 缺 UTF-8 BOM | [`stacks/shell.md`](stacks/shell.md) |
| 字符串少了字符（开头被吞） | 双引号里反引号是转义符 | [`stacks/shell.md`](stacks/shell.md) |
| `bad interpreter` / `$'\r': command not found` | `.sh` 是 CRLF 行尾 | [`stacks/shell.md`](stacks/shell.md) |
| `git add` **整体失败**、报某文件无法索引 | Windows 保留名文件（`nul` 等） | [`stacks/git.md`](stacks/git.md) |
| 命令长时间无输出、像卡死 | 探测/重试循环等待过久 | [`stacks/shell.md`](stacks/shell.md) |
| 改完代码**没生效** | 热重载被关闭 / 浏览器缓存 | [`stacks/python.md`](stacks/python.md) · R-008 |
| 服务起不来 `Address already in use` | 端口被占 | [`stacks/platform.md`](stacks/platform.md) |
| **担心提交/发布带出敏感信息** | 没有强制脱敏检查 | **C-008**（配 `scripts/sanitize-check`） |
| 提交被 pre-commit 拒绝 | 命中脱敏黑名单 | **C-008** · `.sanitize-deny.txt` |
| 首次 push 被拒 `(fetch first)` | 远程已有提交，需 rebase | [`stacks/git.md`](stacks/git.md) |
| **文档里的路径/版本对不上实际** | 改了结构没回头改文档 | **C-007** |

### 测试

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **单独跑通过、放进整套就失败** | 跨请求共享状态（限流/缓存）污染 | **R-003** · **R-009** |
| 大批用例报 403 / 429 | 同上 | **R-009** |
| 加了限流却**完全不触发** | DEBUG 下缓存是 `DummyCache` | [`stacks/platform.md`](stacks/platform.md) |
| **整套测试慢得离谱**（几十上百秒） | 夹具在做生产级哈希/加密，**框架不会自动降级** | **R-013** |
| 最慢用例耗时是**某常数的整数倍** | 同上；用 `--durations N` 一眼看出 | **R-013** |

### 排查工具 / 扫描脚本

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **扫描报告"0 处问题"，但实际有** | 检测脚本自身的假阴性（写错了匹配方式） | **R-014** |
| 审计结论与手工实测矛盾 | 先信实测；工具需要"已知阳性"自测 | **R-014** |

### 改了数据源 / 格式之后

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **没反应、也不报错** | 代码根本没执行（如函数 ref 漏冒号、入口开关没打开） | **R-015** |
| 改成新格式后功能整个失效 | 激活了"为它写但从没跑过"的分支 | **R-015** |
| `Maximum recursive updates exceeded`（递归更新超限 / 页面卡死） | 渲染/回调里写响应式状态，缺"值未变则返回"守卫 | **R-015** |

### 接口 / 数据 / 安全

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| 未登录接口返回 `email` / `username` | 公开接口嵌了完整用户序列化器 | **R-007** |
| `?xxx=abc` 返回 **500** | 用户可控参数未校验 | **R-006** |
| `'int' object is not subscriptable` | 外键序列化成整数，前端当对象用 | [`stacks/python.md`](stacks/python.md) |
| 密码 / 密钥出现在仓库里 | 硬编码；`.gitignore` 防不住**内容** | **R-001** · **R-002** |
| 敏感值已在 git 历史里 | 改文件没用，要轮换凭据 | [`stacks/git.md`](stacks/git.md) |
| 按日期分组**全是 NULL** | MySQL 时区表为空 | [`stacks/platform.md`](stacks/platform.md) |
| 功能"看起来配好了"却走兜底 | 配置缺失被静默吞掉 | [`stacks/platform.md`](stacks/platform.md) |
| 某个 action 该匿名却要求登录 | 覆写 `get_permissions()` 顶掉了 `@action` | [`stacks/python.md`](stacks/python.md) |

### 插件 / 宿主集成

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **装完插件后宿主会话直接崩**（`reading 'kind'`） | 顶层 import 了装不上的包（peer 依赖不会被安装） | [`stacks/dsh-plugin.md`](stacks/dsh-plugin.md) · **C-009** |

### 成本 / 排查

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **上下文消耗快**、费用高但没干什么 | 有东西在**每轮重发**（注入 / 系统提示 / 工具描述） | **C-011** |
| 某插件装上后 token 涨得比预期多 | 注入的消息**进了 session 历史** | **C-011** |
| **推测三次都不对**、改了还是不行 | 在凭印象推断，而不是先造事实 | **C-012** |
| 「应该工作但没工作」，日志里没有线索 | 失败分支被静默跳过了 | **C-012** · **C-009** |
| 不知道某段代码到底有没有被调用 | 没写探针；应该让程序自己报告 | **C-012** |
| **API 成功了，但返回的内容明显偏少** | **静默的部分成功**（只读到了第一块/第一帧/第一页） | **C-013** |
| 读压缩 / 分块 / 流式文件时结果异常小 | 多个 frame/分片，API 只解了第一个 | **C-013** |
| 「没报错」就当成「拿到了全部」 | 没核对完整性指标 | **C-013** |

### 多副本不一致

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| **改了配置/版本，某处显示却不跟着变** | 同一个值被抄在多处，你只改了一处 | **R-011** |
| **三处数据源都对，但还有地方是错的** | 有**测试管不到的副本**（commit message / 文档 / 发布说明） | **R-011** |
| 版本号、枚举清单在不同文件里对不上 | 副本超过 2 个 —— 该收敛到单一来源了 | **R-011** |

### 空 / 等待 / 故障

| 症状 | 很可能的原因 | 详见 |
|---|---|---|
| 用户报"**界面空白/没数据**"，查下来却是正常的 | **等待态和故障态用了同一个显示** | **C-014** |
| 一个 bug 追了很多轮，每次归因都不同 | 起点可能是"**把正常当异常**" | **C-014** |
| 写「暂无数据」 | 它同时盖住了"还没有""取不到""真的是空"三种情况 | **C-014** |
| 排查用的诊断信息一直摆给用户看 | 技术细节应当默认折叠 | **C-014** |
