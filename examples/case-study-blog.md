# 真实案例：从某博客项目的 538 行记录中提炼

这是一次**实际的提炼过程**，用来说明 `core/DISTILL.md` 的四步法怎么落地。
原料：一个 Django + Vue 项目（某博客项目）的开发记录 + 一次完整开发会话。

---

## 提炼前的状态

```
job.md  538 行开发记录
└── ## 必须遵守
    - 只有能使用并且通过测试才能添加到任务完成记录中
    - 每次测试添加的数据，在测试成功后必须进行删除
```

**只有 2 条**。而 538 行里沉淀了大量教训 —— 但它们只以「故事」形式存在，
**下次开发时不会自动生效**。

---

## 逐步提炼

### 案例 A：从"事故"到铁律

**原料**（会话记录里的原始事实）：

> 项目首次推送到 GitHub 后，检查发现三处明文密码进了仓库：
> `backend/config/settings.py` 的 `PASSWORD`、`docker-compose.yml` 的
> `MYSQL_ROOT_PASSWORD`、`项目大纲.md` 里的数据库密码与管理员密码。
> 更讽刺的是：`.gitignore` 明明排除了 `.env`。

**第 2 步 · 筛选**

| 判据 | 通过？ |
|---|---|
| 可复用 | ✅ 任何项目都可能踩 |
| 可执行 | ✅ 能写成"只从环境变量读" |
| 有代价 | ✅ 凭据泄露，要轮换密码 |
| 非显然 | ✅ "我排除了 .env 啊"正是最危险的错觉 |

**第 3 步 · 抽象**

```
个案：这个项目的 settings.py 里有明文密码
  ↓ 抽象一层
技术：Django 的 DATABASES 配置不要写死密码
  ↓ 再抽一层
模式：凭据绝不硬编码（源码 / 配置 / 文档 / 模板 全都不行）
```

**同时抽出了第二条**（这次事故其实是两个不同的错）：

```
个案：.gitignore 排除了 .env，但密码在 settings.py 里，还是泄露了
  ↓ 抽象
模式：忽略规则只能防"未来新增的文件"，防不住"已经写进内容里的值"
```

**第 4 步 · 立卡**

产出 **R-001** 和 **R-002** —— 注意 R-002 是**元层面的规则**，
它纠正的不是某个具体写法，而是**一种错误的安心感**。这类规则最有价值。

---

### 案例 B：从"排查耗时"到铁律

**原料**：

> 给登录接口加了限流（10 次/分钟）后，跑完整测试套件出现 **37 个错误**。
> 根因：几乎所有用例都会调用 `/api/token/` 登录，而限流计数存在共享缓存里，
> 第 11 个之后的用例全部被 429 挡住。

**筛选**：可复用 ✅ / 可执行 ✅ / 有代价 ✅（37 个错误，差点去逐个改用例）/ 非显然 ✅

**抽象**：

```
个案：限流计数器污染了测试
  ↓
技术：DRF 的限流计数存在共享缓存里
  ↓
模式：任何跨请求共享状态的机制，必须提供一句话就能关闭的开关
```

**产出 R-003**，并附带一条**衍生的诊断规则 R-009**：

> 一次改动导致**大批**用例失败时，先怀疑**共享状态污染**，而不是逐个改用例。

**R-009 是从"我们当时差点走错方向"里提炼的** —— 原始记录不只要记「怎么修的」，
更该记「一开始以为是什么」。**误判方向本身就有规则价值**。

---

### 案例 C：从"用户反馈"到铁律

**原料**：

> 用户反馈"我关注加的是粉丝 关注"，附了主页截图。
> 排查发现数字本身是对的，但 `/api/follows/?followed=1` 恒返回 0 条
> —— 粉丝列表接口一直是坏的，藏了很久没人发现。

**抽象**（这次抽出的东西比表面问题更有价值）：

```
个案：粉丝列表接口坏了但没人发现
  ↓
为什么没人发现？因为主页上的数字只是纯文本，点不开
  ↓
模式：数据有、但没有入口能看到时，视为功能未完成 —— 因为错误无法被发现
```

**产出 R-010**。同时发现**修完之后应该做什么**：

```
补上入口后，还应该加一条断言：列表条数 == 计数字段
  ↓
模式：两个地方说同一件事，就必须有一致性测试
```

**产出 R-011**。

---

### 案例 D：一次会话产出了 4 条

同一轮开发里（加"关注/粉丝"弹窗），除了 R-010 / R-011，还提炼出：

| 原料 | 规则 |
|---|---|
| 按钮放进 `<router-link>` 里，渲染成 `<a><button>`，点按钮误触发跳转 | **R-005** HTML 结构必须合法 |
| `?follower=abc` 让后端抛 ValueError → 500；前端加了守卫也没用（改 URL 就绕过） | **R-006** 用户可控参数必须在视图层校验；**前端的校验是体验，后端的校验才是防线** |

## 提炼统计

| 来源 | 原料量 | 产出规则 |
|---|---|---|
| 会话记录（1 次完整开发） | — | L0 ×9、L1 ×3 |
| `job.md` 538 行记录 | 26 个条目 | L0 ×3、L1 ×1、L2 ×5 |
| **合计** | **约 600 行** | **L0 ×12、L1 ×4、L2 ×5** |

**压缩比约 20:1**，而且产出的东西**可执行**（每 L0 条都有检查方法）——
而原始记录只能"读"，不能"执行"。

---

## 这次提炼暴露的一个问题

**原始记录里大量内容无法提炼成规则**，例如：

- 「2026-02-16 核心功能完善：安装 django-filter、配置分页」
- 「2026-04-25 管理后台数据统计仪表盘」

这些是**做了什么**，不是**该注意什么**。它们有考古价值，但没有约束价值 ——
**这就是为什么"记录"不能替代"约束"**，也是本包存在的理由。

---

## 可复用的经验

1. **事故必提炼**：造成过实际损失（安全问题、数据错误）的，一定有规则
2. **误判方向也提炼**：一开始以为是什么、为什么错，比最终修法更有复用价值
3. **元规则最值钱**：纠正"错误的安心感"的规则（如 R-002、R-009），比具体写法更持久
4. **抽到模式层**：抽到"某个框架怎么用"只能留在 L2；抽到"哪类问题该怎么处理"才能进 L0
5. **提炼不出规则是正常的**：600 行里大部分是"做了什么"，只有少数是"该注意什么"
