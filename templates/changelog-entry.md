# 版本条目模板

> 每个版本条目按下面的结构写。**只写事实，不写过程。**
> 判断标准：一个不了解上下文的人读完，能知道「为什么会出这个问题、
> 它造成了什么后果、怎么修的」—— 不需要读你当时的心理活动。

```markdown
## [x.y.z] - YYYY-MM-DD

### <问题一句话概括>            <!-- 用现象命名，如「README 显示过期版本号」 -->

**原因**：<导致问题的机制或遗漏。写具体的东西：文件、配置项、框架行为、数值。>

**问题**：<造成什么后果。能给出可验证的事实就给：报错原文、错误数值、
对照实验、影响范围。>

**解决方法**：<改了什么。列点，写到"改哪个文件/加什么约束"这一层。
如果连带补了测试或规则，一并写出。>

### <第二个问题>                <!-- 一个版本修了多件事就并列多个小节 -->
...
```

## 几条硬要求

| 要求 | 反例 |
|---|---|
| 用现象命名小节 | ✗「一次痛苦的排查」 ✓「README 显示过期版本号」 |
| **原因**写机制，不写"我以为是" | ✗「我一开始猜是缓存」 ✓「版本一致性测试只覆盖源码，未覆盖文档」 |
| **问题**给可验证事实 | ✗「造成很大困扰」 ✓「511 个用例耗时 150 秒；对照实验 5.5 秒，相差 27 倍」 |
| **解决方法**写动作 | ✗「已修复」 ✓「README 改为指向 VERSION；新增测试扫描 README/docs」 |
| 不写用户原话、不写自我检讨、不写"我认为/我纠结" | — |
| 不需要 原因/问题/解决方法 的补充信息，放引用块（`>`），不要单开小节 | — |

## 为什么要有这个模板

2026-10-05 用户指出：变更日志读起来像**讲故事**，而不是记录。

> "我感觉你再讲故事 正常应该是 因为什么原因 造成什么问题 解决方法吧"

规则库 **C-004**（记录要沉淀成规则，不能只写故事）本来就规定了这件事，
但当时没有可执行的格式约束，于是又写成了叙事文。
现在格式由测试强制（`tests/plugin.spec.mjs` 的【变更日志】用例，
从 0.25.0 起生效）。
