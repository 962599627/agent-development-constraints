# 会话记录模板

> 这是**提炼的原料格式**。不用写得很漂亮，但**必须包含"卡在哪"和"怎么出来的"** ——
> 因为规则来自弯路，不来自顺利的部分。

---

```markdown
## <日期> <做了什么>

### 目标
一句话说清这次要达成什么。

### 过程（重点记录弯路的）
- 一开始怎么做的：
- **卡在哪**：（报错原文 / 现象 / 误判的方向）
- 怎么定位的：（哪条命令 / 哪个对比 / 哪个假设被推翻）
- 最后怎么修的：

### 代价
花了多久 / 影响范围 / 是否造成数据或安全问题。

### 这次有没有可以变成"下次自动生效"的约束？
- [ ] 有 → 走 DISTILL.md 提炼，填的是：
- [ ] 没有 → 原因：
```

---

## 为什么这样设计

**① 只记弯路，不记流水账**

顺利的部分没有规则价值。值得提炼的永远是"**以为 A 结果是 B**"的那一刻。

**② 「卡在哪」要贴报错原文**

提炼规则时，报错原文能帮我们判断**触发条件**和**检查方法**；
转述过的描述会丢掉关键线索。

**③ 末尾那问句是闭环的钩子**

开发记录最常见的失效方式：写完之后**没人回头看**。
把"要不要提炼"变成记录模板里的一个待勾选项，提炼才不会被跳过。

---

## 反面示例（这样写，提炼不出东西）

```markdown
## 修复了粉丝列表 bug
改了 FollowViewSet 的 get_queryset，现在可以传 followed 参数了。
```

问题：**看不出根因**。为什么坏？为什么没早发现？下次怎么避免？

## 正面示例

```markdown
## 修复粉丝列表恒返回 0

### 目标
让主页的"粉丝"数字能点开看到明细。

### 过程
- 一开始以为前端没做入口，只加弹窗 → 弹窗是空的
- **卡在哪**：`/api/follows/?followed=1` 返回 0 条，但 profile 上 `followers_count=1`
- 怎么定位的：对比"计数字段"和"列表条数"两个数字，发现矛盾；
  读 get_queryset 发现它只 filter(follower=自己)，把 followed 参数吃掉了
- 最后怎么修的：加 ?followed= 分支

### 代价
这个 bug 在接口层存在了很久没人发现，因为**没有入口去看列表**。

### 能不能变成约束？
- [x] 有 →
  - R-010 入口缺失会让隐藏 bug 永远藏住
  - R-011 两个地方说同一件事就必须有一致性测试
```
